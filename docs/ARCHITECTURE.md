# Openactive — Architecture & Handover Documentation

Open source planning + navigation for hiking and mountain biking. This document is the
single source of truth for the system design. Product assumptions live here; read it
before changing the architecture.

## 1. Product model

- A **tour** is a GPS track (GPX) plus metadata: title, description, stats
  (distance, ascent/descent, elevation extremes), optional source URL.
- A **prepared trip** is a tour flagged for mobile consumption: the home server has
  computed an **offline bundle** (track + description + a manifest of map tiles covering
  the track corridor).
- **Home server-first**: the whole web app runs on the user's own hardware (Pi, NAS,
  Docker). Household accounts distinguish users in one home; there is no cloud, no
  external auth, no telemetry. Privacy is handled by the home server *being* the only server.
- **Assumed offline**: once the phone has downloaded a prepared trip (route + tiles), the
  user is expected to have **no connectivity of any kind** for the rest of the trip —
  neither internet nor access to the home server.

## 3. The ingestion pipeline

`POST /api/tours` (authenticated). Two modes:

### URL mode `{ "url": "https://…" }`
1. If the URL ends in `.gpx` → fetch directly.
2. Otherwise fetch the HTML page and:
   - discover `<a href="…​.gpx">` links (first one wins), resolve absolute,
   - extract title/description from schema.org JSON-LD (`TouristTrip`, `HikingRoute`,
     `Route`, `Place`, `Article`), falling back to OpenGraph/meta tags and article
     containers (see `lib/extract.ts`).
3. Parse the GPX (`lib/gpx.ts`: trk/trkseg/trkpt + wpt fallback), compute stats
   (haversine distance, ascent/descent from `<ele>`).
4. Persist as `data/tours/<slug>.json` (slug collision → numeric suffix).

### Paste mode `{ "gpx": "<xml…>", "title": …, "description": …, "sourceUrl": … }`
Same as above with the provided XML. Intended for GPX files the user already has.

**Extraction quality varies by site.** Sites with schema.org markup work well today;
sites without it fall back to meta tags (weaker descriptions). The intended evolution is
optional per-domain adapters; do not build a general crawler (terms-of-use risk).

## 4. Auth (home server, multi-user household)

- Users created locally via `node scripts/add-user.mjs <username> <password> [displayName]`
  → `data/users.json` (scrypt hash + salt, gitignored).
- `POST /api/auth/login` → signature: `<username>|<expiry>.<HMAC-SHA256>` in an
  httpOnly `oa_session` cookie (30 days). Secret: `data/.secret`, generated by
  `npm run setup` and injected by `next.config.mjs` as `OPENACTIVE_SECRET` at build/start.
- Every other route calls `currentUser()` (via `next/headers` cookies) and returns 401
  otherwise. Sessions are validated by HMAC + expiry; there is no session store.
- Authorization model: **one shared household library** — any household member sees all
  tours/prepared trips. Accounts separate people, not data.

## 5. Prepared trips and offline bundles

`POST /api/tours/<slug>/prepare` (authenticated):
- Computes tiles: Web-Mercator tile covering of the track bbox + 2 km / ~111·cos(lat)-km
  buffer, zoom **11–15 inclusive** (`lib/bundle.ts`, cap 60,000 tiles), plus a rough
  size estimate (25 kB avg/tile).
- Sets `tour.preparedAt`, persists the tour.

`GET /api/tours/<slug>/bundle` (authenticated, 409 if not prepared) returns:

```jsonc
{
  "bundle": {
    "slug": "…", "title": "…", "description": "…", "preparedAt": "ISO-8601",
    "points": [[lon, lat], …],        // track
    "stats": { "distanceKm": …, "ascentM": …, "descentM": …, "minEleM": …, "maxEleM": …, "points": … },
    "zoomMin": 11, "zoomMax": 15,
    "tileCount": 98, "estSizeMb": 2.5,
    "tileCacheBase": "http://<home-server>/api/tiles",
    "tiles": [ { "z": 11, "x": 1099, "y": 743 }, … ]
  }
}
```

`GET /api/tiles/{z}/{x}/{y}.pbf` (authenticated): serves OpenFreeMap vector tiles
(`https://tiles.openfreemap.org/planet/{z}/{x}/{y}.pbf`) from a **home-server disk
cache** (`data/tile-cache/`), filling it transparently on first request. Immutable
cache headers; `x-openactive-cache: hit|miss`. Corrections to note:

- **Known gap**: the web map currently loads the basemap style JSON and DEM terrain
  directly from OpenFreeMap/AWS. For fully LAN-offline operation, cache the style JSON
  and terrain tiles the same way (roadmap item 1).
- Empty (0-byte) vector tiles are legitimate; clients (MapLibre, MapKit+MVT) tolerate them.

## 6. Mobile sync flow ("download prepared trip")

Implemented servers-side (phone client to be built):

```
GET  /api/sync/prepared → [{ slug, title, stats, preparedAt, bundleUrl }]
GET  /api/tours/<slug>/bundle → bundle manifest (+ auth)
for each tiles[]: GET /api/tiles/{z}/{x}/{y}.pbf → store on device (offline store)
```

Everything necessary on the trail is now on the phone. The watch then receives the route
via Watch Connectivity; the watch app never downloads anything itself.

## 7. Apple app design (decided; to be built)

See also README.md. Decisions are intentional — don't revisit without new evidence:

- **iPhone**: SwiftUI + **MapKit**, offline raster/vector tile serving from the app's
  offline store (via the bundle tiles above; `MKTileOverlay`-style rendering),
  `MKPolyline` for the track. Region = the prepared bundle. Sync UI = the three
  endpoints in §5–6, pointed at the home server URL entered once in settings
  (store it in the Keychain, cookies/session too).
- **Apple Watch**: **no maps on the watch.** Backtrack-style GPX navigation: black
  background, minimal breadcrumb polyline + heading cone (SwiftUI `Map`,
  `MapPolyline`, `UserAnnotation` — MapKit for SwiftUI, watchOS 9+), distance to next
  waypoint, off-route haptic alerts, waypoint arrival taps. A HealthKit `HKWorkout`
  hiking/MTB session keeps background location alive with sane battery use. Apple's
  Compass Backtrack has **no public API** — this UI is a rebuild with sanctioned
  frameworks only; avoid the deprecated `WKInterfaceMap`.
- Compliance notes for the Apple side: background location requires `NSLocationWhenInUse`
  + Always usage descriptions and a live workout session or navigation session for
  background GPS; TestFlight review requires route sharing only via your home server,
  no external accounts (Sign in with Apple not required since there are no third-party
  accounts).

## 8. Web map specifics

- MapLibre GL JS 5, OpenFreeMap `liberty` vector style, AWS terrain-tiles DEM
  (terrarium encoding, https://s3.amazonaws.com/elevation-tiles-prod/terrarium/…),
  pitch 65°, terrain-control, track rendered as red `line` layer with dark casing.
- Auto-fits to track bounds on tour select; `TerrainControl` toggles elevation.

## 9. Data contracts

`Tour` JSON (single source of truth, `lib/gpx.ts`):

```ts
interface Tour {
  slug: string;                    // file name in data/tours/
  title: string;
  description: string;
  sourceUrl: string | null;
  createdAt: string;                // ISO-8601
  preparedAt?: string;             // set by prepare endpoint
  points: TrackPoint[];            // { lat, lon, ele|null, time|null }
  stats: TourStats;                 // derived, stored denormalized
}
```

Keep this stably named: the phone app, the web UI and future Postgres migrations all
consume it.

## 10. Limitations / roadmap (in order)

1. Offline LAN: cache style JSON + DEM on the home server (`/api/tiles` only covers vectors).
2. XSS: page HTML from arbitrary URLs is parsed **server-side**; only extracted strings
   are stored/rendered — never inject raw HTML into the DOM, keep it text-only.
3. Bundle is regenerated at download time (tile list recomputed, not persisted) — fine
   now; persist the manifest if the computation ever gets expensive.
4. Concurrency: JSON file writes race if two household members ingest simultaneously;
   acceptable at household scale, fix in the Postgres migration.
5. iOS app skeleton (SwiftUI, SPM, no XcodeGen dependency), then watchOS app.
6. Postgres + PostGIS migration; tour editing; elevation profile chart on the web map.
